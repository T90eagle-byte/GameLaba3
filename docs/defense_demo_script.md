# Сценарий демонстрации проекта на защите

## 1. Подготовка перед показом

Команды:

```powershell
cd C:\GameLR3
git status --short
docker compose up -d
.\.venv\Scripts\python.exe database\scripts\run_tests.py --dry-run
.\.venv\Scripts\python.exe database\scripts\run_tests.py
```

Ожидаемый результат:

- runner показывает package spec/body и tests `01..11`;
- все smoke-tests завершаются с `Failed: 0`;
- `PKG_GENETICS_GAME`: `PACKAGE VALID`, `PACKAGE BODY VALID`;
- `user_errors`: clean.

Если на конкретном стенде Oracle/Docker уже запущен, достаточно выполнить dry-run и полный runner. Не говорить, что тесты прошли, пока они реально не прошли на этом окружении.

## 2. Короткий рассказ на 30 секунд

“БиоСборка — это симулятор генетического конструктора. Пользователь управляет лабораторией, получает заказы на организм с нужными признаками, скрещивает существ, применяет мутации и мутагены. Вся бизнес-логика находится в Oracle PL/SQL package `pkg_genetics_game`: Python-клиент только вызывает API и отображает данные.”

## 5. Если GUI/PySide6 не запускается на стенде

Спокойный fallback-сценарий:

- backend можно доказать через runner `01..11`;
- package compile и `user_errors` показывают состояние PL/SQL;
- smoke-tests проверяют auth/labs, generation, crossbreed, offspring preview, mutations, tasks, sessions, LR2 API и `rating_events`;
- PySide6 остается desktop-версией;
- следующий этап — легкий web-клиент для старого стенда.

Фраза:

“Даже если клиентская оболочка не запускается на конкретной старой ОС, backend полностью проверяется smoke-tests и будет доступен через web-клиент. Игровая логика не зависит от GUI.”

## 6. Что сказать про уровень 5

- Уровень 5 не заявляется как готовый.
- В текущей версии нет вольера, смертности, совета по этике и закрытия лаборатории.
- Подготовлена база: `nutrition_type`, wallet/rating penalties и `rating_events`.
- Экосистема и этика оставлены как roadmap, потому что это отдельный DDL/backend/gameplay трек.
- Цель текущей версии — надежно закрыть уровни 3 и 4.

## 7. Финальная фраза

“Основной упор сделан на корректную backend-логику: данные нормализованы, правила реализованы в PL/SQL package, доступы разделены по сессиям, а ключевые сценарии покрыты smoke-tests `01..11`.”

## Web-demo update: существа и заказы клиента

Для web-демонстрации после входа и создания лаборатории уже можно показать:
1. `/dashboard` — кошелёк, рейтинг, количество существ, активные и выполненные заказы.
2. `/creatures` — стартовую популяцию существ текущей лаборатории.
3. `/creatures/<id>` — фенотип и генотип, полученные из backend cursor.
4. `/tasks` — задания как “Заказы клиента”, выбор существа, проверку и выполнение заказа через package API.

Следующий web-шаг для защиты уровня 3/4: страница скрещивания с `preview_offspring_options` на 3 варианта потомства.

## Web-demo update: скрещивание

Для демонстрации скрещивания в браузере:
1. Открыть `/crossbreed`.
2. Выбрать двух родителей одного вида.
3. Нажать “Показать 3 варианта”.
4. Показать, что preview содержит 3 варианта и помечен `PREVIEW_ONLY`.
5. Объяснить, что preview не меняет лабораторию.
6. Ввести имя потомка и нажать “Создать потомка”.
7. Открыть карточку созданного потомка и показать генотип/фенотип.

## Web-demo update: мутации и мутагены

Для демонстрации уровня 4 в браузере:
1. Открыть `/mutations`.
2. Показать магазин мутаций.
3. Купить мутацию и объяснить, что wallet меняет backend.
4. Применить мутацию к существу и открыть его карточку.
5. Применить `RADIATION` и `CHEMICAL` как рискованные мутагены.
6. Показать, что wallet/rating берутся из backend stats, а web ничего не пересчитывает.

## Web-demo update: история и последствия

Для завершения демонстрации уровня 4:
1. После скрещивания/мутаций открыть `/experiments`.
2. Показать эволюционную линию как последовательность CROSS/MUTATION/MUTAGEN.
3. Открыть `/rating-events`.
4. Показать, почему изменились wallet/rating: покупки, штрафы, награды.
5. Подчеркнуть, что события записывает backend package, а web только отображает.
