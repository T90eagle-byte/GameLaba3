# AI context: "БиоСборка"

## Назначение проекта

"БиоСборка" - игра-симулятор генетического конструктора. Игрок работает в лаборатории, скрещивает виртуальных существ, применяет мутации и мутагены, чтобы получить организм с заданными признаками и выполнить заказы клиентов.

Главные источники знаний:

- `docs/ПСБД_ЛР1.pdf` - исходные требования, инфологическая модель, базовые GUI-сценарии.
- `docs/ПСБД_ЛР2.pdf` - уточненная структура таблиц, полноатрибутная модель, спецификация пакета `pkg_genetics_game`, описание процедур и функций.

## Архитектурный принцип

Основная бизнес-логика остается в Oracle PL/SQL. Python 3.12 используется как GUI и клиент к БД.

Python не должен самостоятельно реализовывать:

- расчет генотипа и фенотипа;
- правила доминирования;
- скрещивание;
- мутации и мутагены;
- проверку выполнения заданий;
- начисление наград, рейтинга и игровой валюты.
- чтение `dbms_output` как источник GUI-данных.

Python должен:

- подключаться к Oracle;
- вызывать процедуры и функции PL/SQL;
- отображать курсоры и OUT-параметры;
- получать GUI-данные только через OUT-параметры, `sys_refcursor` и функции с простыми типами;
- передавать пользовательские действия в пакет;
- обновлять экраны после ответа БД;
- показывать ошибки и уведомления.

`dbms_output` допускается только для ручной отладки PL/SQL и демонстрационного текстового вывода, но не является контрактом Python-клиента.

## Текущая PL/SQL-точка входа

В ЛР2 все программные модули объединены в пакет:

```sql
pkg_genetics_game
```

Пакет содержит блоки ответственности:

- пользователь и сессии: `register_user`, `login_user`, `logout_user`, `update_user_profile`, `hash_password`;
- лаборатории: `start_new_lab`, `load_lab`, `switch_lab`, `exit_lab`, `delete_lab`, `list_user_labs`;
- статистика: `show_lab_stats`, `get_lab_stats`;
- существа: `show_creatures`, `get_creatures_cursor`, `get_genotype_cursor`, `get_phenotype`, `rename_creature`;
- генетика: `get_dominant_allele`, `get_inherited_allele`, `get_linked_allele_set`, `calculate_punnett_probabilities`;
- эксперименты: `crossbreed`, `make_experiment`, `apply_mutation`, `apply_mutagen`, `show_mutation_history`;
- задания: `show_tasks`, `check_task`, `complete_task`;
- магазин мутаций: `show_mutation_shop`, `buy_mutation`;
- стартовая генерация: `generate_starting_creatures`, `create_creature_of_type`.

На старте реализации лучше сохранить единый пакет `pkg_genetics_game`, потому что он прямо описан в ЛР2. Позже, если преподаватель разрешит, его можно разделить на внутренние пакеты по областям, но внешний контракт для Python лучше оставить стабильным.

## Принятые архитектурные решения MVP

1. Используем 6 типов существ из ЛР2:
   - хрящевые рыбы;
   - костные рыбы;
   - ракообразные;
   - моллюски;
   - черепахи;
   - млекопитающие.
2. Игровая авторизация MVP строится на таблице `users`.
3. Oracle-роли и grants используются для доступа приложения к схеме БД, а не как отдельный Oracle-пользователь для каждого игрока.
4. В таблице `genes` обязательно предусматриваются поля `species_type`, `dominance_type`, `linkage_group`.
5. В таблице `creatures` предусматриваются отдельные фенотипические поля только для часто отображаемых признаков. Полный фенотип формируется и возвращается через `get_phenotype`.
6. Python-клиент не использует `dbms_output`; все GUI-данные возвращаются через OUT-параметры, `sys_refcursor` или функции с простыми типами.

## Основные игровые сущности

- Пользователь - игровой аккаунт и владелец лабораторий.
- Сессия - активный вход пользователя в игру.
- Лаборатория - сохраненное игровое состояние пользователя.
- Существо - экземпляр организма в лаборатории.
- Ген - наследуемый признак или группа признаков.
- Аллель - конкретное значение гена.
- Генотип - набор пар аллелей существа по генам.
- Фенотип - проявленные признаки существа, вычисляемые из генотипа.
- Эксперимент - история скрещивания, мутации или мутагенного воздействия.
- Мутация - покупаемый тип изменения генотипа.
- Мутация в лаборатории - запас купленных мутаций.
- Задание - заказ клиента на нужные признаки.
- Задание в лаборатории - статус задания для конкретной лаборатории.
- Маркер задания - требуемые аллели для выполнения задания.

## Поток Python -> Oracle

1. Python открывает соединение с Oracle через клиентскую библиотеку.
2. GUI вызывает `pkg_genetics_game.login_user`.
3. PL/SQL проверяет учетные данные, создает сессию и возвращает `session_token`.
4. Python хранит токен только как состояние клиента и передает его в процедуры, где он нужен.
5. Игрок выбирает лабораторию через `list_user_labs` + `load_lab` или создает новую через `start_new_lab`.
6. GUI получает данные через курсоры, OUT-параметры и функции с простыми типами: статистику, существ, генотипы, магазин мутаций, задания.
7. Любое действие игрока выполняется процедурой пакета: скрещивание, мутация, покупка, проверка задания, удаление лаборатории.
8. После действия Python заново запрашивает актуальные данные у PL/SQL.

## Важные ограничения

- Не переносить бизнес-логику в Python.
- Не менять архитектуру БД без необходимости.
- Использовать Oracle `PACKAGE` / `PACKAGE BODY`.
- Соблюдать `snake_case` для файлов, каталогов, Python-модулей и будущих SQL-объектов, если это не конфликтует с уже утвержденными материалами.
- Не создавать миграции, GUI и PL/SQL-реализацию до отдельного этапа.
- Не проектировать GUI вокруг `dbms_output`.

## Ранее спорные вопросы, теперь решенные

- 5 базовых видов из ЛР1 считаются минимальным уровнем требований; в MVP берем 6 типов существ из ЛР2.
- Игровые пользователи хранятся в таблице `users`; Oracle grants нужны для приложения и схемы.
- `genes.linkage_group` включается в DDL, потому что без него не работает сцепленное наследование.
- `creatures` получает ограниченный набор часто отображаемых фенотипических полей, а полный фенотип остается результатом `get_phenotype`.
