# Шпаргалка соответствия требованиям для защиты

## 1. Краткая позиция

Проект уверенно закрывает уровень 3: есть 6 видов, базовые признаки, генетическая модель, скрещивание, задания и стартовая генерация существ.

Проект закрывает уровень 4 в адаптированной форме: есть неполное доминирование, кодоминирование, сцепленные гены, мутации, случайные мутагены RADIATION/CHEMICAL, риск через штрафы кошелька/рейтинга и история экспериментов. Формулировка про “волко-собаку” адаптирована под многовидовую “БиоСборку”: лаборатория выполняет заказы клиента, подбирая родителей и применяя мутации для получения нужного фенотипа.

Уровень 5 не заявляется как реализованный: нет полноценной экосистемы, смертности, совета по этике и автоматического закрытия лаборатории. Есть backend-база для будущего развития: питание как признак, штрафы, рейтинг, кошелек и `rating_events`.

Backend сильнее минимальных требований за счет Oracle PL/SQL package `pkg_genetics_game`, справочников `ref_*`, строгих FK, многопользовательских сессий, stateless preview потомства, smoke-tests `01..11` и объяснимой истории `rating_events`.

## 4. Что НЕ заявлять

- Не заявлять полноценную экосистему/вольер.
- Не заявлять смертность особей.
- Не заявлять совет по этике как отдельную механику.
- Не заявлять автоматическое закрытие лаборатории за нарушения.
- Не заявлять уровень 5 как готовый.
- Говорить честно: это roadmap уровня 5; текущая версия надежно закрывает 3/4 и имеет backend-базу для будущего развития.

## 5. Быстрые ответы на каверзные вопросы

**Где у вас волко-собака?**  
В исходной формулировке это пример эволюционной линии. В “БиоСборке” модель обобщена: не одна волко-собака, а 6 видов существ. Эволюционная линия — это путь через скрещивания и мутации к фенотипу, который требуется в заказе клиента.

**Где 3 варианта потомства?**  
Backend считает вероятности потомства через `calculate_punnett_probabilities`, а `preview_offspring_options` возвращает ровно 3 stateless preview-варианта по умолчанию. Эти варианты не создают существ и нужны именно для показа перед реальным `crossbreed`.

**Почему задания — это заказы клиента?**  
Потому что task описывает требуемый результат, а `task_markers` задают признаки, которые нужно предъявить. Лаборатория подбирает или выводит существо под этот заказ.

**Где риск от мутагенов?**  
В `apply_mutagen`: RADIATION/CHEMICAL стоят деньги, дают штраф рейтинга и создают случайно измененное существо. Это проверяется tests `05`, `07`, `10`.

**Почему Python не считает генетику?**  
Так правильнее для этой лабораторной: бизнес-логика находится в Oracle PL/SQL package `pkg_genetics_game`, а Python только вызывает API и отображает данные.

**Что делает `rating_events`?**  
Это журнал причин изменения рейтинга и кошелька: награда за задание, покупка мутации, штраф мутагена. Он не заменяет `labs.wallet` и `labs.rating`, а объясняет их изменения.

**Почему уровень 5 не реализован?**  
Потому что уровень 5 требует отдельной экосистемы: вольер, баланс хищники/травоядные, смертность, совет по этике и закрытие лаборатории. Это крупный следующий этап, и его рискованно добавлять перед защитой.

**Чем проект сильнее минимального уровня 4?**  
Есть `ref_*` справочники, строгие FK, session isolation, runner `01..11`, LR2-compatible package API, stateless offspring preview, `rating_events` и отсутствие gameplay SQL в Python-клиенте.

## Web-показ требования “3 варианта потомства”

Теперь требование можно показать не только backend-тестом `11_offspring_preview_smoke_test.sql`, но и через web route `/crossbreed`:
- выбрать двух родителей;
- нажать “Показать 3 варианта”;
- web вызывает `preview_offspring_options` и показывает 3 stateless preview-карточки;
- реальное создание потомка выполняется отдельно через `crossbreed`.
